# Поле боя: декор оружия, извлечение костей, флаги — технический план
Дата: 21 ноября 2026. Проект: Tears of Ink, Minecraft 1.21.1 Fabric, Java 21.

> **Статус: документ разработки, НЕ реализованный код.** Автор поручил изучить существующие активы и подготовить самостоятельный технический план для будущей работы и передачи между чатами. **Не начинать внедрение/рисование без дальнейшего решения автора о составе сцены, конкретном арте и размещении.** Технические решения ниже, кроме отдельно отмеченных пожеланий автора, — предложения помощника. Никаких новых художественных заглушек, изменений старых моделей, анимаций и текстур этим документом не разрешено. Основной контекст — [MICROLOCATIONS_AND_WORLD_TRACES_2026-11-21.md](MICROLOCATIONS_AND_WORLD_TRACES_2026-11-21.md).

## 0. Прямое новое требование автора (сохранить для следующих чатов)

- Для наполнения поля боя **повторно использовать существующие авторские модели оружия**, которое уже реально применяется в игре, а также **отдельные модели оружия Бледных патрулей**: копьё, щит, арбалет и другие подходящие части. У патрульных оно находится **на отдельных костях внутри общего .bbmodel существа**. Автор согласен дополнительно нарисовать необходимые ресурсы после согласования, что именно требуется.
- **Не трогать** предметы/модели оружия, которые автор пока не анимировал, не проработал и не завершил. Простое наличие .json или .bbmodel в репозитории **не означает** художественного разрешения использовать его в поле боя.
- Декор: мечи, воткнутые в грунт, копья, щиты, арбалетные болты, оружейные группы. **Без игровой коллизии** для мелких объектов, чтобы игрок мог свободно проходить сквозь них; не должны вести себя как лут или игровые оружейные предметы.
- Автор спрашивает о **реющих на ветру флагах/знамёнах**, интересуется реализуемостью и сценой поля боя. Внешний вид, символы, эпоха, целостность, число и движение знамен ещё не согласованы.
- Автор прямо поручил составить **технический план «для себя» и сохранить**, чтобы следующий чат мог подхватить работу. Конкретное размещение, состав, будущие авторские модели и художественные требования будут обсуждаться **позднее**.

## 1. Инвентаризация действительных ресурсов (проверено по GitHub main 21 ноября)

### 1.1. Геометрия патрульных: 3 готовые независимые группы

| Объект | Авторский файл | Группа в Blockbench | Фактическая структура | Игровой Java-экспорт |

| Арбалет бледного арбалетчика | `blockbench/pale_soldier_crossbowman.bbmodel` | `crossbow`, вложена в `hand_r/hand_r3` | **7 кубов**, включая вложенный `cube_r1`, pivot `[-6,3.5,-2.5]`, локальная ротация X = −90° | `client/entity/PaleCrossbowmanModel.java`: `hand_r3.addOrReplaceChild("crossbow", ...)` |

Отдельные исходные текстуры для моделей существ в моде уже есть:
- `assets/tears-of-ink/textures/entity/pale_spearman.png` (Blockbench-атлас 64×64);
- `.../pale_shieldbearer.png` (128×128);
- `.../pale_crossbowman.png` (64×64).

В .bbmodel текстуры вложены base64 и группы связаны через UUID в `groups`/`outliner`, **а не через имя каждого куба**. При извлечении обходить дерево UUID, выбирать дочерние элементы нужной группы, применять всю цепочку трансформов и перерассчитать смещение/центр для мирового декора. Не брать только прямых детей: у `crossbow` есть вложенная группа. **Не забирать вместе с оружием кубы руки.** Исходные `.bbmodel`, PNG, текущие `Pale*Model` и анимации не изменять.

**Вывод:** копьё, щит и арбалет не нужно заново рисовать ради первого статичного декора. Нужно экспортировать копии соответствующих **геометрических поддеревьев** в клиентские world-модели, сохранив UV/цвет/многоосевые повороты. Потребуется проверить, что при извлечении не теряется переворот/сдвиг из анимационной иерархии.

### 1.3. Щиты игрока и болты

- Щиты Души имеют 3D JSON в `models/item/shield/ram.json` (**9 элементов**) и `shield/mercy.json` (**17 элементов**), с собственными текстурами. Они **не включены автоматически**: автор просил использовать уже готовое оружие, а не превращать любое сюжетное/обетное снаряжение в исторические останки на поле боя.
- Бледные арбалетные болты: в моде есть `textures/entity/projectiles/pale_bolt.png`, а текущий `PaleBoltRenderer` — наследник ванильного `ArrowRenderer`, **отдельной .bbmodel болта не обнаружено**. Для неподвижного болта в земле потребуется либо корректная статичная world-модель по существующей текстуре, либо небольшой новый художественный ресурс от автора. **Не ставить в мире живые `PaleBoltEntity` ради декора.**
- Знамён/флагов как готовых ресурсов в дереве мода нет; заготовки и формы не выдумывать без авторского решения.

## 2. Правильная архитектура массового статичного декора

**Цель: много видимого оружия, почти нулевой постоянной серверной работы, но измеряемая цена клиентского рендера.**

1. **Обычные статические блоки без BlockEntity, без Entity.** Группы декора `battlefield_*` с `noCollission()`, `noOcclusion()`, пустой collision shape, `noLootTable()`, без randomTick/serverTick/AI и без подбираемого инвентаря. Сервер хранит block state как обычное состояние мира; не ведёт активной симуляции сотен мечей.
2. **Модели через blockstate + статический baked block model**, который попадает в обычный рендер чанка (желательно с помощью имеющихся JSON-моделей; для сложной геометрии при необходимости `FabricBakedModel`/бэйк на загрузке ресурспака). Не делать сотни `ItemDisplay`, `ArmorStand`, `ItemEntity`, `BlockEntityRenderer` на отдельный меч.
3. **Повороты и наклон:** seed-детерминированный выбор небольшого списка вариантов `FACING` × `POSE` (например, воткнут вертикально, под углом, лежит). Не обещать произвольные 360° через обычное ванильное `blockstate` без готовой модели/трансформов. Критично проверить UV, нормали, позицию режущей кромки и погружение в грунт; ориентация должна задаваться **относительно мирового пола**, не от анимационной кисти NPC.
4. **Кластеры:** если композиция умещается в одном мире-блоке/небольшом объёме, предпочтительно выпечь комбинацию нескольких моделей в **одну статичную модель** (щит + копьё, 2 болта и т. п.). Можно создавать модули из нескольких блоков, если габариты велики. Кластеры не требуют сущностей/специальных тиков. Повторное использование текстуры допускается; не копировать PNG на каждый поворот.
5. **Высокие копья/большие клинки:** у моделей, сильно выступающих за один блок, проверить culling, тени, освещение, отсечение по секциям/чанкам и доступность прохода; если нужна многоблочная обвязка, разместить через корректный footprint, но **без игровой коллизии**. Не держать игровую модель за пределами рассчитываемых рендер-границ без теста.
6. **Генерация:** количество и набор декора выбираются по seed **после** резервирования поля боя и проектирования его грунта; разместить на проверенной конечной высоте поверхности, избегая воды, путей, входов и защитных зон; не врезать меч в воздух/камень фундамента без основания. Группы ориентируются на локальный уклон/направление «следов боя», но **распределение и художественная композиция ещё не утверждены**. Не переделывать дороги.
7. **Не всё бесплатно:** несколько сотен статических блоков не вызывают тики сущностей, но занимают память чанков, добавляют полигоны, время построения чанковых мешей и работу GPU. Не обещать «серверу вообще всё равно», измерять chunk build, FPS, память и сетевую нагрузку при первом посещении.

**Технический вариант по умолчанию:** 2–3 семейства блоков (`battlefield_sword_decor`, `battlefield_spear_decor`, `battlefield_shield_decor` и т. п.) с небольшим числом состояний позы/направления; создавать очередные семьи только при реальном отличии геометрии/поведения. Регистрировать без выдачи в обычный Creative/JEI и без рецептов, пока автор не разрешит игроку получать декор; не перехватывать игровые ID оружия и не использовать `ItemStack` в качестве world-данных.

## 3. Конвейер «извлечь оружие патрульного»

**Рабочая спецификация для будущего Codex:**

1. Открыть актуальные `blockbench/pale_soldier_{spearman,shieldman,crossbowman}.bbmodel`; сверить совпадение нужных групп с действующими `Pale*Model`. **Ничего не удалять из исходников.**
2. Подготовить отдельный скрипт-конвертер, например `tools/battlefield/export_decor.py` (имя рабочее), который разбирает `groups` и `outliner` Blockbench по UUID; собирает дочерние кубы только нужного bone; учитывает parent pivot, rotation, mirror/UV, вложенные кости и texture atlas.
3. Применить inverse/normalization к текущему позированию оружия: собственные оси/поворот группы, привязка к руке и общая orientation не должны переноситься как наклон от NPC. Для `spear`, `Shield`, `crossbow` зафиксировать один общий понятный world-pivot (кончик/хват/основание в зависимости от объекта) и масштаб.
4. Генерировать **новые производные ресурсы** в `models/block/battlefield/` и `blockstates/`, при возможности ссылаться напрямую на исходную PNG сущности (`tears-of-ink:entity/pale_spearman` и т. п., с проверкой загрузки sprite/атласа). Если преобразование UV слишком сложно — сделать **отдельный скопированный/выделенный PNG** только после согласования с автором; не править оригинальную текстуру существа.
5. Сохранить воспроизводимость: manifest «source path + group UUID/name + texture + generated paths», контроль экспорта (количество исходных кубов, контроль UV, отсутствие кубов руки, отсутствие потерянных child-костей), сравнение размеров/позы в preview или Minecraft.
6. Результат экспорта — статический декор, **не новый предмет для выдачи NPC**. Поведение копейщика, щитовика, арбалетчика и их анимации не менять.

Для игровых клинков алгоритм проще: использовать существующий готовый `models/item/*.json` как геометрический источник, а не парсить Blockbench-кости. Конвертировать item-display-relative transforms в статичную world-геометрию, правильно смещать в блок, проверять кубы за пределами 0–16 и все грани. Поддержать **один внешний whitelist источников**, чтобы не включить случайно недоработанные авторские модели при следующем запуске.

## 4. Флаги: отдельный путь, не массовый декор

**Реющие знамёна технически возможны и без физической симуляции ткани на сервере.**

- Рекомендуемый старт для **редких** флагов (рабочий ориентир 2–6 на поле, автор ещё не выбирал число): блок-основание / древко с **одной BlockEntity без серверного тика** и клиентским `BlockEntityRenderer`. Это не сотни живых сущностей; блок-сущность всё равно имеет стоимость хранения и синхронизации при загрузке чанка, но не обязана каждый тик посылать пакеты.
- У флага авторская сегментированная 3D-геометрия: крепление, 3–5 условных секций ткани, понятные pivot для каждой секции, 1-2 текстуры. На клиенте использовать плавную периодическую функцию или авторский loop Blockbench, смещать фазы по координатам, чтобы флаги не двигались синхронно. **Никакой попытки автоматически реализовать «настоящую физику» ткани или wind simulation на сервере.**
- Ткань может быть рваной, флаг может лежать на земле (такой вариант статичен). Два-три вида движения, фракционные символы, цвет, форма, размер, размещение и набор вариаций — **автор решает позже**. Не генерировать за него фракционные эмблемы.
- Клиентский BER должен быть связан с chunk/section, учитывать visibility и разумную дистанцию отрисовки (особенно важны переходы при локальном расширении тумана на поле). Не делать клиентский отдельный тик по всем флагам независимо от видимости. Важна стабильность при перезагрузке ресурспака, смене мира, на dedicated server и в multiplayer.
- Если окажется, что на больших полях нужны десятки/сотни анимированных полотен, **пересмотреть архитектуру** на батчинг/более дешёвую геометрию, не масштабировать BER вслепую. Первый этап — один реющий флаг для проверки стоимости и качества.
- Возможен более простой вариант с ванильной логикой анимированного баннера как исследовательский ориентир, но это не означает, что уже существует готовый рендер авторского флага.

## 5. Встраивание в генерацию поля боя

Сопутствующая концепция закреплена в [общем документе](MICROLOCATIONS_AND_WORLD_TRACES_2026-11-21.md): поле — микролокация с редеющим лесом, пнями, смешанной землёй, кратерами, крупным открытым пространством, следами оружия и **плавно более дальним туманом**; последний эффект не входит в первый пилот.

**Планируемый порядок работ:**
1. **Нулевой этап (сейчас):** конспект и инвентаризация; ничего не внедряем.
2. **Пилот A — только ресурсы:** по одному извлечённому `spear`, `Shield`, `crossbow` и **одному одобренному автором** готовому мечу, без нового рисунка. Временное размещение/команда проверки только после задания; сравнить размеры/UV с живыми моделями, проверить отсутствие коллизии. По окончании убрать технические стенды из мира/ресурсов, если это лишь проверка, но не удалять авторский арт.
3. **Пилот B — много статичных объектов:** тестовая сцена в **отдельном тестовом мире/новых чанках**, постепенно увеличивать число однотипных и смешанных моделей, измерять влияние на сервер/MSPT и на FPS, chunk rebuild, memory; сравнить со сценой без декора. Выявить реальный бюджет, **не придумывать заранее обязательную цифру «300 мечей»**.
4. **Пилот C — terrain/worldgen:** детерминированный план поля, резервирование и проверка границ, адаптация грунта, постепенное редение леса; chunk-local генерация без принудительного открытия соседних чанков, защита всех действующих храмов, дорог, мостов, застав, лагерей, руин и новых структур. Проверить порядок worldgen/vegetation и разные порядки загрузки чанков, исключить разрывы рельефа. **Не менять рабочие InkLandsLayout/InkRoadsFeature/TempleNetwork лишь ради пилота.**
5. **Пилот D — флаг:** один клиентски анимированный авторский флаг на отдельной тестовой площадке; затем измерения нескольких одновременно видимых.
6. **Художественная сборка и баланс обнаружения:** только после описания автора собирать композиции, плотность оружия, редкость, видимость от следов до поля, туман, структуры, лут/существа (если предусмотрены), точные числа полей на мир.

**Не смешивать** новый статический набор с правкой мировой генерации в одном непроверяемом коммите. У каждого этапа отдельная приёмка. При невозможности безопасно поставить поле на конкретный участок — расширить поиск кандидатов и документировать причины отказа, а не молча убрать запланированную локацию; **не ломать охраняемые места ради квоты**.

## 6. Тесты и критерии приёмки (ещё НЕ проводились)

- **Art preservation:** SHA оригинальных `.bbmodel`, `.png`/анимаций и игровых item JSON не меняются; конвертер не переписывает исходники; выбор модели — по approved whitelist.

## D-114 — Новая архитектура «поле боя → зоны → блоки» (обсуждается с автором; реализация НЕ начата)

### 1. Суть предложения автора — принято как направление проектирования

Автор предложил **не независимую россыпь предметов по полю** и **не ручное составление каждой сцены**. Требуется трёхуровневая логика:
1. **Поле боя:** цельная визуальная/пространственная картина со следами прежнего события, рельефом, растительностью, границами, возможным расступающимся туманом; поле не должно быть набором несвязанных POI.
2. **Зоны:** локальные композиции со своей понятной логикой/«историей»: щит, частично вдавленный в землю; несколько мечей; перекрещённые копья; арбалетные болты в щите; другие сюжеты после обсуждения референсов. Зона связывает предметы по смыслу и пространству, а не просто создаёт квадрат с плотностью.
3. **Блоки:** элементарные неподвижные визуальные модели (уже существуют бесколлизионные spear/shield/crossbow), их трансформы и, когда согласовано, составные декоративные комбинации. Для мелкого декора прежний принцип **без коллизии, сущностей и тиков** остаётся.

**Автор отдельно подтвердил работу текущего прототипа D-113 в Minecraft** («Работает, да»). Это подтверждение функциональности, но не исчерпывающая художественная приёмка всех размеров и поворотов.

### 2. Предлагаемая помощником схема реализации (НЕ окончательно утверждённый дизайн)

```text
BattlefieldPlan (один план по seed, глобальная территория)
├─ BattlefieldIdentity / Environment: общая «география события»,
│  геометрия поля, разрывы леса, кратеры/грунт/пни, возможные линии боя
├─ ZonePlan[]: тематические участки с назначением и связями
│  ├─ intent / story hook (не придумывать лор — механическое имя/роль)
│  ├─ footprint / terrain tolerance / exclusion envelope
│  ├─ anchor(s) and relationship rules
│  ├─ required props, optional props and weighted alternatives
│  ├─ orientation / facing / relative proximity / overlap constraints
│  └─ DecorPlacement[]: final block state, position, pose, world pivot
└─ PeripheralClues: отдельные следы боя по мере приближения,
   связаны с полем, не являются случайными независимыми россыпями
```

Предложение: **декларативные рецепты зон / композиционная грамматика** (данные, а не сотни вручную сохранённых NBT-сцен). Рецепт хранит отношения между объектами, например «щит — центр композиции», «болты торчат из щита под допустимыми углами», «оружие лежит или торчит рядом в пределах допустимого радиуса», «опорный грунт обязателен». Генератор может варьировать ориентации, мелкие смещения, количество, позы и ассортимент **в пределах художественно согласованных диапазонов**. Одинаковый seed даёт одинаковое поле. Художественные сюжетные композиции типа «болты в щите» могут потребовать **единую статичную baked-модель**, если отдельные блоки не дадут точной привязки на границах ячеек или усложнят отсечение/освещение; это технический выбор после референсов.

Три **потенциальных уровня** зоны для будущего исследования (не список утверждённых зон):
- **Ядро/ключевой эпизод:** наиболее читаемая композиция с обязательными предметами;
- **Реакция окружения:** земля, поваленная растительность, следы, разбросанное снаряжение на связанных расстояниях;
- **Переход/рассеяние:** редкие детали, которые приводят взгляд игрока к эпизоду и связывают соседние зоны.

Не делать все зоны одинаковыми кругами или повторять одно сочетание оружия. Связность всего поля должна быть видна даже при редком декоре. Положение зон и ориентацию предметов следует определять **после** общей географии поля; зоны должны учитывать друг друга, следы подхода/пути, свободные проходы, границы чанков, разную высоту, защищённые строения и край редеющего леса. Окончательные «стороны»/фракции, история сражения и символика флагов — **решает автор**, не выводить их автоматически из оружия в репозитории.

Источники приведены в самом чате от 21.11.2026 и сюда занесены как описания, **не скопированы/не перенесены в ресурсы игры**.

**Прямая позиция автора:** референсы крайне базовые, показывают **идею/настроение, а не образец «сделать точно так же»**. Не нужно сдерживать размеры: **огромное оружие допустимо, если выглядит эстетично**. Автор предложил попробовать существующую **модель ровного прямого меча**, увеличенную для большого кинематографичного клинка. Не назначать конкретный предмет без проверки и согласования, не выдумывать владельца/сюжет, не копировать конкретные узнаваемые композиции побуквенно.

### Вывод из изображений: зоны должны работать и на дистанции, и вблизи

**Ранее D-114:** «поле боя → смысловые зоны → статичные блоки», взаимосвязанные маленькие истории (болты в щите, перекрещённые копья и т. п.).

**Уточнение после референсов:** одного набора локальных историй недостаточно. Требуется также **сценография поля** — узнаваемые силуэты в тумане, пространственные ритмы и контраст масштабов. Визуальная иерархия:
1. **Силуэт всего поля:** общее направление склонов, участки леса/прореживания, вид из подходящих точек, дальние доминанты, свободные просветы между массами оружия. Большое поле не должно выглядеть как ровный ковёр из одинаковых мечей.
2. **Зональные массивы:** «скопление клинков»/«поле воткнутых мечей», отдельный монументальный клинок, локальная сцена нескольких предметов; каждый тип имеет свою плотность, доминанту, направление, границы, пустоты, связи с соседними зонами.
3. **Близкие композиции:** щит с болтами, упавшее оружие, пересечённые копья, клинок в камне; детали работают только при приближении, но поддерживают общий силуэт.
4. **Отдельный декор:** извлечённые модели патрульных и позднее согласованные игровые клинки, масштаб и поза по правилам конкретной композиции.

**Не утверждённые, а предлагаемые для обсуждения зональные мотивы:**
- **Поле мечей:** разновысокие, неравномерные скопления воткнутых клинков с направлениями и просветами, не одна сетка; особенно хорошо на склонах.
- **Доминанта:** один особенно крупный меч/несколько существенно более крупных клинков как визуальный ориентир, с более мелким оружием на разных расстояниях; что это означает в мире — решает автор.
- **Клинок, поглощённый местностью:** оружие из-под земли, камня, корней, возможно цепи (по двум фото). Не означает утверждённую механику цепей/скального камня; это композиционная тема для обсуждения.
- **Следы столкновения:** сочетание щитов, копий, болтов и разбросанных клинков, локальная логика сцены из D-114.
- **Периферия/переход:** единичные клинки и следы разрушения до основного открытого поля — как раньше предлагал автор.

Зоны не обязательно должны иметь одинаковую иерархию, размеры или одни и те же мотивы. **Не обязательно каждое поле битвы делать «кладбищем мечей»**: возможно разные типы целой сцены; точный выбор — за автором.

### Как преобразовать референсы в процедурную грамматику, без десятков вручную построенных NBT

Предложение помощника — обогатить данные `ZonePlan` параметрами **визуальной композиции**: `scale_palette` (обычные / акцентные / монументальные), `density_profile` (ядра и разрежение), `dominant_anchor` (опциональный центр силы), `orientation_field` (согласованное направление или намеренный хаос), `negative_space` (просветы, дорожки, обзор), `terrain_affinity` (склон/камень/прогал), `transition_to_neighbours` (переход к другим эпизодам). Это **вариант архитектуры, не утверждённые игровые параметры**. Следить, чтобы предмет не пересекал другой без намерения: «перекрещённые копья» и «болты в щите» — **намеренное**, остальные случайные пересечения нежелательны.

Сначала выбирать силуэт и доминанту целого поля, затем места смысловых зон и их основные объекты, после — детали и разрежение; в конце оценивать восприятие игроком **с уровня глаз и в текущем тумане**, а не только математическую правильность seed-планировщика. Предусмотреть отдельные сценарии/ракурсы для локаций, где туман должен расступаться (обсуждавшаяся авторская идея), но не менять систему тумана сейчас.

### Масштабирование готовой модели — технические границы

- Для **обычного/умеренно увеличенного** статичного оружия можно производить производные block JSON с масштабированием исходной геометрии и UV, применяя нужные pivot/наклон. Сохранять исходные item-модели и их текстуры **неизменными**.
- Для **монументальных** клинков обычный ванильный baked block JSON с диапазоном координат примерно **−16…32 единицы** относительно одного блока не позволяет бесконечно масштабировать геометрию. При размере в несколько блоков нужно **сегментировать монументальную модель на части / многоблочную статичную композицию** (желательно без BlockEntity и без server tick для массового декора), либо обдумать единичный специальный клиентский рендер с корректными границами. Это не «просто поставить scale=10»: заранее планировать footprint, рендер-секции/чанки, UV, culling, устойчивую фиксацию и корректную опору/врезание в грунт.
- **Крупный клинок не должен искусственно превращаться в коллизионное препятствие**, если автор хочет проходить сквозь художественный декор. Но для огромного объекта возможность/невозможность прохода и взаимодействие с рельефом определить отдельно; не фиксировать за автора.
- Не следует использовать десятки `ItemDisplay` или создавать сотни BlockEntity только для обычных клинков. При массивном повторении важен **рендер-бюджет клиента**, не только MSPT. Оценить фруструм, GPU, chunk build и лаги при появлении открытого поля после плотного тумана. Ни величина монументов, ни плотности не утверждены.
- **Кандидаты-прямые мечи (подлежат авторскому допуску):** `models/item/pale_longsword.json` и `models/item/pale_linear_great.json` уже существуют как 3D артефакты; степень визуальной прямизны и художественную уместность каждого нужно оценить вместе с автором в игре/превью. Никакое незавершённое оружие автоматически не включать. Другие мечи/отдельный авторский гигантский клинок возможны позже по его решению.
- При наличии монументального клинка его placement/surface mask выбирать **раньше** мелких предметов, иначе большое оружие может пересечь дороги, сооружения, границы поля или стать невидимым в лесу. Для больших клинков проверять постройку игрока и сохранность чанков, не переделывать существующие защищённые объекты.

### Контрольное повторное осмысление (предварительно, до согласования арта и реализации)

- **Первый взгляд:** референсы показывают не набор «анимационных» предметов, а ритм вертикальных линий, большие контрасты, точечные истории вблизи, открытый обзор. Сильные сами по себе, даже без врагов и добычи.
- **Второй взгляд:** огромный клинок может потерять эффект, если таких клинков очень много; наоборот, поле из сплошной равномерной решётки мелких мечей станет похожим на питомник или декоративную ферму. Поэтому нужны управляемые пустоты, локальные скопления, разная частота, углы и несколько уровней масштаба.
- **Техническая проверка:** звёздочка — существующий `battlefield_shield` уже имеет многоблочную геометрию и требует смещённого anchor; у монументального меча эта проблема будет существенно сложнее. **Прежде чем просить автора рисовать монументальный меч, желательно измерить пригодность существующих прямых 3D моделей и испытать способ многоблочного отображения только по дальнейшему поручению.**
- **Открыто:** сколько и каких типов полей, допустимы ли несколько гигантов в одном поле, где должен быть главный фокус, должны ли цепи присутствовать, какие клинки/фракции относятся к историческому событию, степень разрушенности и наличие реально гигантского оружия в лоре, вариации тумана, дополнительные художественные ресурсы. **Не выдавать эти предположения за принятое ТЗ.**

**Следующий шаг:** обсудить с автором предпочтительные композиционные мотивы и список допустимых прямых клинков/дополнительного арта, затем составить ведомость; по D-114 сначала полностью согласовать зонирование и повторно перепроверить логику, **затем** писать генератор.

## D-123 — 3D-позирование авторского декора вместо вертикальной россыпи (21 ноября 2026)
После игровых скриншотов автор указал на художественный недостаток D-122: «щит стоя, копья стоя, флаги» — это лишь поставленные рядом блоки. Правильный композиционный узел должен иметь **позу/контакт/пересечения, обусловленные предметной историей**: слегка погружённый, опрокинутый щит; копьё, опирающееся на щит; второе почти упавшее копьё; брошенный арбалет; знаменная линия как отдельный пространственный мотив. Требования мира (большой граф зон, поиск многих кандидатов, защищённые дороги, деревья, дым/туман, старые миры) остаются непрерывно действующими и не выдаются за готовый worldgen.

## D-126 — Проверка настоящего направления острия, не рукояти (21 ноября 2026)
**Обнаружена ошибка D-125 по отзыву автора:** в 8 скопированных из item JSON декорах исходные диагональные оси геометрии имели рукоять у **низкого X+Y**, лезвие/голову у **высокого X+Y**. Схема D-125 `Z+45°`, опора `(minX,minY)` ошибочно втыкала в грунт рукоять. **Техническое правило D-126 заменяет этот участок описания D-125**: для всех восьми mesh следует применять `translate(-maxX,-maxY)` относительно собственной bbox, затем `Z -135°` (в матричном порядке: `Z(-135) * Translate(-maxX,-maxY)`), и только после него внешние независимые scene yaw/pitch/roll и положение в мире.

Проверка коллизий/пустот на сервере обязана повторять этот же перенос с нормализацией px/16 и последующим поворотом; нельзя корректировать лишь визуальную матрицу клиента. Поворот самих исходных игровых предметов не менять. Для почти горизонтально лежащих клинков ограничивать отрицательный sink, чтобы рукоять не уходила под землю даже после разворота; статичные сцены кешировать как раньше. Контроль: (а) у острия `localY≈0`, у рукояти `localY>0`, (б) при всех сценовых позах клинок соприкасается с землёй, а рукоять не заглубляется, (в) старые индексы и сущности не мигрируют. **Требуется** игровой осмотр после CI для подтверждения читаемости конкретных авторских моделей.
