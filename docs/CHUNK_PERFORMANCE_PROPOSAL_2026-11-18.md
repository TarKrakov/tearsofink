# Производительность загрузки и генерации Чернильных Земель

**18 ноября 2026. Статус:** техническое предложение по запросу автора об ускорении чанков. Не утверждённое поручение изменять генерацию. Код не изменён, профилирование пока не проведено. После D-048 магистрали и созданные штольни — защищённый результат; не изменять географию, существующие структуры, размеры мира, плотность руд, деревья или дальность тумана ради ускорения. Не мешать параллельной работе Codex над фонтанами.

## Факты и ограничения измерений

Отчёт [D-048](PALE_FOREST_ADIT_PILOT_TASK.md#результаты-реализации-d-048): серверный расчёт возрождения без привязки после прогрева на seed 20261118 занял 14 мс до штолен и 3 мс после; до загрузки стартового храма на seed 777 — 241,1 и 196,9 с, на холодном seed 42 — 131,2 и 156,3 с. Это неодинаковые сценарии, измеренные на общей машине с двумя ядрами и несколькими JVM, не измерение времени одного чанка, не доказательство ускорения/регрессии новой генерации. Клиентский тайм-аут при холодном возрождении остаётся открытым. Проблема существовала до штолен. Изолированный профиль нужен прежде сравнений.

## Конкретные места для исследования

- `ModDimensions.templeSpotAndFountain` при отсутствии cache синхронно запрашивает 5×5 чанков через lands.getChunk, затем просматривает область 53×53×71, до 199439 позиций. Кэш WeakHashMap<ServerLevel,...> существует только в памяти. Рассмотреть получение позиций из фактической трансформации NBT стартового храма (или сохранение фактической позиции при построении), bounded lookup и проверку безопасного места; совместимая загрузка старых миров с ограниченным fallback без массового сканирования. Не предполагать, что все 25 чанков обязательно нужны.
- `Prologue.preloadArrival` уже начинает предварительную загрузку ticket radius 6; `Travel.keepRespawnLoaded` / preloadRespawn использует radius 3. Проверить, почему загрузка не успевает к переходу/смерти; не добавлять ещё один неограниченный preloader, не считать tickets гарантией готовности чанка. Приоритет минимальной области назначения, остальные чанки по штатной загрузке; перенести подготовку на существующие естественные паузы пролога, не блокировать тик синхронным ожиданием. Для возрождения применять совместимый безопасный подход с учётом синхронного API DimensionTransition; не переносить игрока куда попало, не менять респаун и не обещать асинхронную смерть без проверки API. Согласовать с реализацией FOUNTAIN_TRAVEL_CODEX_TASK.md, переиспользовать безопасный загрузчик при возможности; не держать все фонтаны загруженными.
- `InkLandsLayout.roadHeight/buildRoadProfiles`: первая инициализация под synchronized рассчитывает все 5 профилей; для каждой точки с шагом 8 запрашивает surface/floor (getBaseHeight) плюс valleyHeight. Кэш уже есть; профилировать первый расчёт, повторные одинаковые запросы и ожидание блокировки, затем рассмотреть точное переиспользование height samples и сохранение детерминированных результатов по seed/генератору/версии. Не менять формулы, шаг, сглаживание, число дорог или мосты. Не запускать worldgen методы в произвольных потоках без гарантий thread safety. Отдельно проверить порядок инициализации roadBridge, чтобы не изменить результат моста.
- `InkLandsLayout.roadAt` вызывается из многих features/структур: для подходящей дороги перебирает точки d−12…d+12 шагом 0,5. Измерить CPU/allocations; при подтверждении горячего участка рассмотреть bounded per-chunk cache точных ответов с учётом halfWidth (сохранить порядок выбора, double precision, ранний выход) или консервативный пространственный индекс. Не заменять точный расчёт приблизительной прямой; не кэшировать без ограничений координаты целого мира. Профилировать и FinalCleanupFeature, генерацию растительности и vanilla noise/lighting, а не предполагать, что дороги единственный расход.
- `AditStructure.findGenerationPoint`: кэш sites по RandomState в synchronized WeakHashMap, единовременный AditSites.plan с проверками высот/руин/дорог всех кандидатов. Уже существует кэш, не пересчитывать сеть на каждый чанк. Измерить задержку первой инициализации и удержание lock; оптимизировать только если подтверждено, сохранить 20 входов/координаты и порядок генерации. AditLightingMixin и сохранённые pieces не переписывать без доказанной причины.

## Рекомендуемый порядок отдельной задачи Codex

1. Зафиксировать текущий main как baseline после работы над фонтанами. Изолированные прогоны одной JVM, одинаковый JDK/heap/thread count/view-distance, одни seed 777, 42, 20261118 и порядок загрузки, несколько повторов. Разделить cold generation (новый мир), disk load (сохранённые чанки) и warm cache (готовые чанки). Замерять wall time, p50/p95 задержек тика/чанка, CPU, allocation/GC, память, время первого входа/возрождения/переноса. Для интерпретации использовать JFR/доступный профайлер и собственные точечные таймеры (не логировать каждую колонку). Различать время генерации и время передачи/отрисовки клиентом.
2. Устранить подтверждённые блокирующие загрузки назначения, ограничить временные tickets, очередь/timeout, сохранять/переиспользовать валидные позиции стартового фонтана/прибытия. Проверить оба обета, первый вход, старые миры, респаун с кроватью/фонтаном/без них, дальний перенос, отключение и мультиплеер. Не считать маскировку лагов ускорением CPU.
3. Оптимизировать наиболее дорогую функцию только по профилю, небольшими отдельными коммитами. Повторить измерения; не обещать множитель ускорения до замеров. Профиль/снимки дорог до/после на одних seed, реальные координаты и проходимость штолен, храмов, озера, Вестников, существующие блоки/лут/руды/биомы не меняются. Учесть ранее выявленную вариативность порядка биомных features: сравнивать один порядок, не вводить диагностические правки в релиз. Не менять существующие формулы лишь ради скорости.
4. При необходимости предложить **опциональную** предгенерацию ограниченной области серверного мира между игровыми сессиями, с оценкой диска и времени. Она переносит стоимость, не делает генерацию быстрее. Не запускать автоматически для всех игроков, не генерировать весь круг радиусом 2200, не требовать внешний мод. Отдельно рассмотреть серверную дистанцию просмотра/симуляции как пользовательскую настройку, не менять их глобально в моде.

Рабочая рекомендация: после текущих штолен/телепортации провести короткий отдельный профиль; если есть тайм-ауты и блокирующие задержки — исправить их до масштабного добавления фауны. Не превращать оптимизацию в бесконечный перепроект мира. Итог — реальные цифры до/после и невыполненные проверки, отдельное одобрение при необходимости изменить географию. Пока не запускать Codex автоматически.
