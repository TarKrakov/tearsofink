# Правила разработки Tears of Ink

Эти правила действуют для всего репозитория. Техническая карта и границы подтверждённых сведений: [docs/PROJECT_STATUS.md](docs/PROJECT_STATUS.md).

## Ответственность и решения

1. Пользователь — автор, геймдизайнер и руководитель проекта. Все окончательные игровые решения принимает он.
2. Codex отвечает за программную реализацию, исправления, архитектуру и техническую документацию в рамках согласованной задачи.
3. До изменения изучать существующие классы, вызовы, регистрации, ресурсы и зависимости затронутой системы.
4. Не переписывать работающие системы исключительно ради рефакторинга. Не расширять задачу без необходимости.
5. Не изменять утверждённые механики, характеристики и баланс без согласования с автором. Числа в Java и игровых JSON также относятся к балансу.
6. Не удалять и не заменять модели, текстуры, анимации, звуки и другие художественные ресурсы автора без разрешения.
7. Заглушки создавать только по согласованной задаче; явно отмечать их назначение и границы. Наличие старой заглушки не разрешает её замену или создание новых.

## Технические требования

8. Сохранять совместимость с Minecraft 1.21.1, Fabric и существующими зависимостями. Целевая Java мода — 21 (`options.release = 21`); для Gradle в облачной среде используется JDK 25. Не путать JVM сборки и целевую версию байткода.
9. Избегать ненужных новых библиотек и зависимостей. Не обновлять Gradle и версии зависимостей попутно с другой задачей.
10. Учитывать многопользовательскую игру, сохранение данных и синхронизацию клиента и сервера: проверять серверную обработку действий, пакеты, вход/выход, смерть/возрождение и перезапуск при изменениях соответствующих систем. Не переносить клиентские классы в общий код. Сохранять совместимость существующих сохранений либо отдельно согласовывать миграцию.
11. Выполнять изменения небольшими проверяемыми этапами. Сначала определить затронутые точки входа и ожидаемое поведение, затем внести минимальное изменение и проверить результат.
12. После изменений запускать соответствующие проверки. Для кода — сборку через существующий wrapper (`bash ./gradlew build` с JDK 25); для документации — проверку diff, ссылок и соответствия исходникам. Игровые и серверные проверки выбирать по затронутой системе. Не запускать генерацию ресурсов, если задача не требует изменения ресурсов. Никогда не утверждать, что проверка прошла, если она не выполнялась; отдельно указывать заблокированные и невыполненные проверки.

## Git, отчётность и неопределённость

13. В отчёте перечислять изменённые файлы, выполненные проверки и их результаты, ошибки, ограничения и оставшиеся задачи. Отделять подтверждённое исходным кодом от сведений только из документации и вопросов автору.
14. Не выполнять массовые удаления, необратимые изменения, слияния в `main` или публикацию релизов без явного согласия. Работать в отдельной ветке; включать в коммиты только файлы задачи и не затрагивать посторонние изменения пользователя. Создание PR не означает разрешения на merge.
15. Не считать устаревшие комментарии и планы автоматически актуальными. При противоречиях фиксировать вопрос для автора и описывать фактическое поведение кода. Не объявлять сложную или необычную систему неработающей без воспроизводимого подтверждения. Автор ранее проверял реализованные механики в Minecraft; статический обзор не заменяет эту проверку и не является новой игровой проверкой.

## Обязательный журнал решений

16. Постоянно фиксировать **согласованные решения и значимые авторские уточнения** в [`docs/DECISIONS.md`](docs/DECISIONS.md): дата, статус (утверждено / идея / вопрос), формулировка, мотив и затронутые системы. Перед подготовкой ТЗ и изменением механик проверять этот журнал вместе с актуальным кодом и `docs/PROJECT_STATUS.md`. Не объявлять вывод анализа принятым решением; после обсуждения обновлять журнал отдельным документационным PR либо вместе с реализацией, не сливая без разрешения автора. Исторические творческие документы не являются текущим каноном без подтверждения автора.
